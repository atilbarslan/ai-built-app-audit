Executive summary

This report reviews a salon and barbershop booking app in two parts: whether every feature works the way it was asked for (functional review), and whether it is secure. It documents the fixes applied and is written for the business owner: each finding explains what was found, why it matters for the business, and what was done about it.

The app is built on solid foundations. The database keeps each salon's data separate, visitors cannot read the tables directly, and the system already prevents two bookings landing on the same person at the same time. The automated security scan offered by the build platform reported no issues at the time of the audit (October 2026); that same report notes it cannot catch every possible risk.

The issues found are subtler than missing basics: the booking and permission rules were enforced only in the app's screens, not on the server. Anyone who talks to the system directly, bypassing the screens, could do things the screens never allow. That is the thread running through the most serious findings.

Of 24 findings (19 from the security review, 5 from the functional review), the 2 High and most Medium issues are fixed or materially reduced; the rest are documented with clear recommendations. Every fix is backed by an automated test that failed before the change and passes after it. Of the 19 requirements in the original request, 15 are now met, 4 partly and none missed. The original app is preserved unchanged for before-and-after comparison.

The biggest risks in plain terms

  • A stranger who knew a client's phone number could change that client's name and email.
  • A single visitor could flood the booking calendar and client list with fake entries and make it unusable.
  • Any staff member could delete a client and that client's entire history.
  • Bookings could be created at closed times (03:00, closed days, or years ahead) by bypassing the app.
  • Typing someone's email into the staff list could silently give them access to your client data.
  • Stylists could miss appointments: the calendar hid appointments outside opening hours, and a stylist saw only part of a client's history, so the AI briefing and reminder were built from partial data.

Latest test run (2026-10-13): 55 tests: 50 passed, 1 skipped (an environment-dependent time-zone demonstration), 4 recorded as to-do (functional items left as recommendations).

How severity is rated

Every finding is rated on the same short scale, judged by who could exploit it and what it would affect:

What was done well

Not everything needed fixing. These are the parts the app already got right:

  • Each salon's data is isolated from every other salon's (verified by tests).
  • Anonymous visitors cannot read database tables directly; public actions go only through a small set of controlled functions.
  • Double-booking the same staff member at the same time is prevented by the database itself.
  • Prices on past bookings are snapshotted, so later price changes do not rewrite history.
  • The powerful server key never reaches the browser.
  • The AI features run as the signed-in user, so they cannot reach another salon's clients.

Additional hardening applied

  • Anonymous visitors had database-level table privileges by default, leaving the access rules as the only line of defence; those privileges were removed, so anonymous visitors can now use only the controlled public functions.
  • Phone numbers are normalised to one format so the same client is not stored twice.

Design decisions (intentional behaviour)

Some behaviour that an automated scan might flag is deliberate - product choices for this app, not defects:

  • Owners and staff can place, move or cancel appointments outside published opening hours and on closed days. This is a deliberate product choice for this app: salons routinely take off-hours or day-off appointments, so booking management inside the app keeps full control of the calendar. The public booking page that clients use is still held to the opening-hours, open-day and 21-day advance rules (see BH-01), and the system still prevents two appointments from overlapping on any path.
SEC-01 High
Partially fixed

A visitor could change an existing client's name and email

What was found

The public booking flow identified clients by phone number. A booking made with an existing client's phone number overwrote that client's stored name and email with whatever was typed.

Why it matters for the business

Anyone who knew (or guessed) a client's phone number could rename that client and change their email, and the new booking attached to that client's history and notes. This corrupts the client list and could be used to impersonate or harass a client.

What we changed

We changed the rule that saves a client from a public booking so it never overwrites a client who already exists: it keeps the stored name and email and only fills in blanks. We also added a field that records the name typed at booking time and show it to staff on the client screen when it differs, so they can check it is the same person.

Where

Files: drizzle/migrations/0001_audit_hardening.sql, src/routes/_authenticated/customers.$id.tsx
Commit: 17f8c81, 255d78d

How we verified it

Test '[#1]' in public-booking.test.ts and http-e2e.test.ts failed on the original app (the client's name was overwritten) and passes after the change (the stored name is unchanged).

What remains

A stranger who knows a client's phone number can still attach a booking to that client's record without changing it. Closing this fully needs a one-time code sent to the phone at booking time.

Finding 1 of 24
BH-02 High
Partially fixed

No limit on public bookings

What was found

A single anonymous visitor could create an unlimited number of bookings; there was no rate limit or quota.

Why it matters for the business

An attacker could fill the calendar and client table with fake entries and make the system unusable for the salon.

What we changed

We added two limits to the booking function: at most 5 upcoming bookings per phone number, and at most 10 bookings per salon per minute.

Where

Files: drizzle/migrations/0001_audit_hardening.sql
Commit: 408b033

How we verified it

Two tests in public-booking.test.ts (the per-phone cap and the per-salon burst) accepted the flood before and stop it after.

What remains

Per-visitor rate limiting and a CAPTCHA need a layer in front of the app (the booking call comes straight from the browser), and the AI features still need a per-user usage limit. The per-salon quota (10 bookings per minute) is shared by all visitors, so someone who keeps sending bookings can use it up and block real customers while the attack lasts; it limits fake records, not availability. Likewise, the per-phone limit (5 upcoming bookings) lets someone who knows a customer's phone number fill that customer's quota, because phone numbers are not verified (SEC-01). Both are why the recommended edge-layer controls (per-IP rate limiting, CAPTCHA) and OTP phone verification matter.

Finding 2 of 24
BH-01 Medium
Fixed

Bookings could be made at impossible times

What was found

The rules about opening hours, open days and how far ahead clients may book existed only in the app's screens. Calling the booking service directly, the only server check was that the time was not in the past.

Why it matters for the business

Someone bypassing the app could create appointments while the salon is closed, outside opening hours, or years in the future. The public calendar stops reflecting reality and staff cannot trust it.

Design decision: These rules apply to the public booking page only. When the owner or staff create or move a booking inside the signed-in app, they are deliberately allowed to book outside opening hours and on closed days (see Design decisions). Overlap is still prevented on every path.

What we changed

We added the booking rules to the server function that creates a public booking: it now checks the salon's open days, opening hours, a 21-day limit, and that the chosen time lands on a valid 15-minute slot, all judged in the salon's own time zone. We also added a time-zone setting to each salon so the checks use the right clock.

Where

Files: drizzle/migrations/0001_audit_hardening.sql
Commit: 28d4163

How we verified it

Tests '[#2] 03:00', '[#2] years in the future', '[#2] closed day' and '[BH-01] 15-minute grid' in public-booking.test.ts were accepted on the original app and are rejected after the change.

Finding 3 of 24
SEC-03 Medium
Fixed

Staff could do more than their role should allow

What was found

Any staff member could edit and delete client records, and could read every booking in the salon. Deleting a client also deleted that client's entire booking and note history.

Why it matters for the business

A single stylist could wipe a client's whole history, or browse other staff members' clients - well beyond 'see your own calendar'.

What we changed

We changed the database access rules: staff may read clients (needed to keep notes), but only the owner may add, change or delete them; and each staff member can read only the bookings assigned to them, while the owner reads all.

Where

Files: drizzle/migrations/0001_audit_hardening.sql
Commit: 3c08384

How we verified it

Tests in role-matrix.test.ts and http-e2e.test.ts show staff can no longer edit or delete clients, and a test in pentest.test.ts shows a staff member sees only their own bookings. All failed before and pass after.

What remains

Staff can still read the salon's whole client list (names, phone, email, notes), because they need it to keep notes; only their booking view is limited to their own. Restricting the client list per staff member would be a separate product decision. Owners can also still delete a client (which removes that client's history); a soft-delete that hides instead of erasing is recommended. This change also limited the client history staff saw on the client page and in the AI buttons; the functional review caught that and it was fixed as FN-01.

Finding 4 of 24
SEC-04 Medium
Fixed

Staff invitations joined people without consent

What was found

Adding an email address to the staff list silently linked that person to the salon the next time they signed in, with no acceptance step.

Why it matters for the business

A person could be given access to a salon's client data without ever agreeing to join, and the behaviour was unpredictable when an email belonged to more than one salon.

What we changed

We removed the automatic linking on sign-in and added an explicit invitation: the invited person sees a pending invite and must click Accept, and only an invite addressed to their own email can be accepted.

Where

Commit: 2ade4e1

How we verified it

Tests in pentest.test.ts confirm sign-in no longer auto-joins, a different email cannot accept the invite, and the invited person can accept their own.

Finding 6 of 24
SEC-05 Medium
Fixed

Missing security headers

What was found

The app sent none of the standard browser security headers (such as a content security policy or anti-framing header).

Why it matters for the business

The site could be embedded invisibly in a malicious page to trick clients (clickjacking), and browser defences against injected scripts were weaker than they should be.

What we changed

We added a content security policy and the other standard security headers to every server response, and allowed the specific resources the app actually needs so nothing breaks.

Where

Files: src/lib/security-headers.ts, src/server.ts
Commit: 2865255

How we verified it

Test in security-headers.test.ts checks the headers are present, and a live check confirmed the booking and sign-in pages load with no policy violations.

What remains

The policy still permits inline scripts (it has to, because the app's framework injects them as the page loads), which weakens its protection against injected scripts. Tightening it to a stricter, nonce-based policy is a recommended follow-up (see the roadmap).

Finding 7 of 24
SEC-06 Medium
Recommendation

Login session stored in the browser

What was found

The login session token is kept in the browser's local storage.

Why it matters for the business

If a script-injection flaw ever occurred, an attacker could read the session and take over the account.

How to fix

  1. Store the login session in a secure, HttpOnly cookie so page scripts cannot read it.
  2. Keep the content security policy added in SEC-05 in place as an added layer.

Finding 10 of 24
SE-02 Medium
Partially fixed

Time slots used the visitor's time zone

What was found

The list of free time slots was calculated using the visitor's device time zone, while the salon's opening hours are stored without a time zone.

Why it matters for the business

A client in another region saw shifted times and could book a slot that is not actually open at the salon; two clients in different regions picking the same time sent two different real times.

What we changed

We compute the available time slots in the salon's time zone instead of the visitor's, and pass the salon's time zone through to the booking page.

Where

Files: src/lib/format.ts, src/routes/book.$slug.tsx, drizzle/migrations/0001_audit_hardening.sql
Commit: 28d4163

How we verified it

Test in timezone.test.ts passes in three different time zones (it produced shifted times before the change).

What remains

Found in the functional review: the public page still asks for busy times over the visitor's own day, so for a visitor far east of the salon an evening slot can show as free and is then refused by the server (no double booking is possible). Calendar days and AI message times also follow the device or a fixed zone rather than the salon's. Recommended (roadmap).

Finding 11 of 24
SE-03 Medium
Recommendation

Lists and dashboard will under-report at scale

What was found

Lists and the dashboard have no paging and silently stop at the first 1000 rows; revenue is added up in the browser.

Why it matters for the business

As the salon grows, the dashboard and lists will quietly show incomplete or wrong totals.

How to fix

  2. Add paging to the client and booking lists so nothing is cut off at 1000 rows.

Fixed

Staff saw only part of a client's history

What was found

This problem was caused by one of this audit's own security fixes, not by the original app, and the functional review caught it. After staff were limited to their own calendar (SEC-03), the client page and both AI buttons read the same limited data. Finding 16 of 24
SEC-09 Low
Mitigated

AI reminder could be steered by note content

What was found

Client name and notes flow directly into the AI prompt, and the AI-written reminder is sent from the salon's own phone number.

Why it matters for the business

Someone could try to steer the reminder message (for example to insert a link) by writing instructions into a client's note or name.

What we changed

We wrap the client's name and notes as data (clearly marked as not instructions) before sending them to the AI, and strip any links out of the reminder before it can be sent.

Where

Files: src/lib/ai-sanitize.ts, src/lib/ai.functions.ts
Commit: 74b21bb

How we verified it

Test in ai-sanitize.test.ts removes a link smuggled into a simulated AI reply and keeps normal text. No live exploit was attempted against the production model, which is not reachable in this test setup.

What remains

The hard control here is stripping links from the outgoing message. Wrapping the notes as data reduces, but cannot fully guarantee against, an AI model being steered; this is why the status is 'Mitigated' rather than 'Fixed'. Keep untrusted text out of the instruction part of the prompt as the AI model changes.

Scope and how to re-run the tests

Scope

Testing was limited to a locally running copy of the app and a separate test project with the same database structure applied to it. No hosted or production environment was accessed. All test data is fictitious.

Re-running the tests

The findings are backed by an automated test suite. To re-run it against your own test project, provide connection details in a local environment file (not included in this report) with these variable names:

  • AUDIT_SUPABASE_URL
  • AUDIT_SUPABASE_PUBLISHABLE_KEY
  • AUDIT_SUPABASE_SECRET_KEY
  • AUDIT_DATABASE_URL
  • AUDIT_GEMINI_API_KEY (only for the AI prompt-injection test)
  1. npm install
  2. Apply the original database structure (migration 0000).
  3. Apply the hardening changes (migration 0001).
  4. Apply the functional fixes (migration 0002).
  5. Load the fictitious test data (fixtures).
  6. Run the test suite. With only the original structure applied, the finding tests fail (proving the issue); with migrations 0001 and 0002 applied, they pass (proving the fix).
